# BMS — System Design

> **Phase:** Architecture  
> **Date:** 30 March 2026  
> **Status:** Complete — ready for development

---

## Summary

BMS is a multi-tenant SaaS web application built on Next.js and Supabase. It is designed as a single unified product: any lodge, hotel, or tourism operation signs up, configures their departments from a template library, and starts operating — no custom development required. Ziwa Rhino and Wildlife Ranch is the first tenant.

The system's architecture is shaped by three constraints that are non-negotiable for the Ugandan market:
1. **Offline-first** — the app must read and write without live internet
2. **Multi-tenant from day one** — every table is org-scoped; there is no Ziwa-specific code
3. **Mobile money as primary payment** — MTN MoMo is first-class, not an add-on

The intelligence layer — operational alerts, morning brief, cross-department anomaly detection — is the product's core differentiator. Everything else (forms, stock, comms, payments) exists to feed clean data into it.

---

## How it works

A **department head** opens BMS on their phone. If they're online, the form loads from Supabase; if not, it loads from IndexedDB. They complete their daily report and submit. The submission writes to IndexedDB immediately (instant feedback), and the service worker syncs it to Supabase when connectivity returns. They never see an error for being offline.

An **admin or GM** opens the dashboard each morning. Waiting for them is the morning brief — generated by a nightly scheduled job at 5:00 AM UTC (8:00 AM Kampala). The brief shows three things: alerts requiring action, yesterday's key metrics, and any notable trends. It requires no navigation — it is the landing screen.

A **stock manager** receives a requisition from a department. They review it, approve or reject, and the stock record updates. When a new delivery arrives, they record the inbound transaction. If any item falls below minimum threshold, an alert fires automatically and appears on the dashboard within seconds.

A **guest or receptionist** creates an invoice, records a payment (cash or MTN MoMo). If it's mobile money, a webhook from the GovBill API marks the invoice paid automatically. The transaction appears in the morning brief's revenue summary.

## Data model

### Tenancy — the foundation of everything

Every table that contains tenant data carries `org_id`. RLS policies enforce that queries only return rows where `is_org_member(org_id)` is true. There is no application-layer tenant filtering — the database enforces isolation.

```sql
-- Core helper functions (SECURITY DEFINER so RLS policies can call them cheaply)

CREATE OR REPLACE FUNCTION get_user_org_id()
RETURNS UUID LANGUAGE SQL STABLE SECURITY DEFINER AS $$
  SELECT org_id FROM users WHERE id = auth.uid()
$$;

CREATE OR REPLACE FUNCTION is_org_member(target_org_id UUID)
RETURNS BOOLEAN LANGUAGE SQL STABLE SECURITY DEFINER AS $$
  SELECT EXISTS (
    SELECT 1 FROM users
    WHERE id = auth.uid() AND org_id = target_org_id AND active = true
  )
$$;

CREATE OR REPLACE FUNCTION get_user_role()
RETURNS TEXT LANGUAGE SQL STABLE SECURITY DEFINER AS $$
  SELECT role FROM users WHERE id = auth.uid()
$$;
```

RLS policy pattern for every tenant-scoped table:
- **SELECT:** `is_org_member(org_id)` — all org members can read
- **INSERT:** `is_org_member(org_id) AND [role or ownership check]`
- **UPDATE/DELETE:** role-gated (owner/admin/manager for most tables)

## Intelligence trigger model

### Event-driven (database triggers → Edge Functions)

| Event | Trigger | Action |
|---|---|---|
| Report inserted | `AFTER INSERT ON reports` | Check if all departments have submitted for `report_date`; create `report_overdue` flags for any that haven't by the deadline |
| Stock transaction inserted | `AFTER INSERT ON stock_transactions` | Recalculate `current_quantity`; if below `minimum_quantity`, insert `intelligence_flags` record with severity based on how far below |
| Requisition inserted | `AFTER INSERT ON requisitions` | Create notification for the org's admin/manager users |
| Payment inserted | `AFTER INSERT ON payments` | Update `invoices.amount_paid` and status; create notification |

Triggers call `pg_net.http_post` to invoke an Edge Function for anything requiring external calls (WhatsApp, AI). Pure database work (quantity updates, flag inserts) is done directly in the trigger function.

### Scheduled (pg_cron)

```sql
-- Morning brief — runs at 05:00 UTC (08:00 EAT) for all organisations
SELECT cron.schedule(
  'generate-morning-briefs',
  '0 5 * * *',
  $$
    SELECT net.http_post(
      url := current_setting('app.supabase_url') || '/functions/v1/generate-morning-brief',
      headers := jsonb_build_object(
        'Authorization', 'Bearer ' || current_setting('app.service_role_key'),
        'Content-Type', 'application/json'
      ),
      body := '{}'::jsonb
    )
  $$
);
```

The `generate-morning-brief` Edge Function:
1. Queries all active organisations
2. For each org, aggregates yesterday's reports, stock movements, payments, and open flags
3. Calls GPT-4o for a 2–3 paragraph narrative
4. Writes to `intelligence_briefs` with `brief_date = yesterday`

### On-demand (Edge Functions called by frontend)

- `analyse-department` — takes `org_id`, `department_id`, `date_from`, `date_to`; calls GPT-4o with the department's report data for the period; returns structured analysis
- `reconcile-stock` — takes `org_id`, `item_ids[]`; computes expected quantity from transaction history vs. current recorded quantity; returns discrepancy report

## Offline-first architecture

### How it works

The service worker (Workbox) intercepts all Supabase REST API calls. Read requests are served from cache if offline. Write requests (form submissions, stock updates) are stored in IndexedDB and queued for sync.

```
Write flow:
  User submits form
  → Form component writes to IndexedDB (local_id generated client-side)
  → UI shows "Saved — syncing..." 
  → Service worker sync queue picks it up
  → On connectivity: POST to /api/sync → Supabase upsert → sync_queue.status = 'synced'
  → UI shows "Submitted"

Read flow (offline):
  User opens form
  → Service worker checks cache for department schema
  → If cached: serve immediately (stale-while-revalidate)
  → If not cached: show offline notice, load from IndexedDB
```

### What is cached in IndexedDB

| Data | Cached | Reason |
|---|---|---|
| User's department form schema | Yes | Needed to render forms offline |
| Own department's last 7 days of reports | Yes | For reference while completing today's report |
| Stock items list (name + unit) | Yes | For inventory_grid field type |
| Org and user profile | Yes | For context and auth headers |
| Other departments' reports | No | Not needed for field operations |
| Admin dashboard data | No | Admin users are expected to have connectivity |

### Conflict handling

At Ziwa's scale (one submission per department per day, per department, from a single device), conflicts are unlikely. The `UNIQUE(org_id, department_id, report_date)` constraint on `reports` prevents duplicates. The sync endpoint uses upsert with conflict on `sync_id`. If a conflict occurs, the server version wins and the client is notified to reload.

For stock transactions (which could theoretically conflict if two devices process the same requisition offline), the design avoids this: only the stock manager role can process inbound stock, and they operate from a single device.

### UI indicators

- **Synced:** No indicator shown (silence = good)
- **Offline, no pending queue:** Small persistent "Offline — working locally" banner at bottom of screen
- **Offline, queue pending:** "Offline — 3 items queued" with a sync icon
- **Syncing:** Brief "Syncing..." state, dismissed on success
- **Sync failed:** Persistent warning with "Retry" button

## Key design decisions

### 1. Service worker + IndexedDB over PouchDB

PouchDB with a custom Supabase sync adapter would give CouchDB-style conflict resolution. But it introduces a second document-store paradigm alongside PostgreSQL, and at Ziwa's scale (single submissions per department per day), conflicts are near-zero. Service worker + IndexedDB is adequate, well-documented, and keeps the stack coherent. Decision: Option A from research — IndexedDB first, PouchDB only if conflict frequency proves it necessary.

### 2. JSONB form schema over normalised field tables

A fully normalised schema would have `form_sections`, `form_fields`, `field_options` tables. This is more queryable but adds significant complexity to the form renderer (5+ table joins to build a form) and makes template customisation a multi-table operation. JSONB for form schemas is the correct choice here: the schema is read as a unit, written as a unit, and validated as a unit. The tradeoff is that you cannot easily query "all fields of type `inventory_grid` across all departments" — but that query is not needed in V1.

### 3. `current_quantity` maintained by trigger, not application code

The application code could calculate current stock by summing `stock_transactions`. This is clean but slow as history grows. Maintaining `current_quantity` as a denormalised field on `stock_items`, updated by a trigger after every transaction, is standard practice. The trigger is deterministic, runs in the same transaction as the insert, and keeps queries fast. The design accepts the tradeoff: `current_quantity` is always consistent with `stock_transactions`, but if a migration or direct DB manipulation skips the trigger, they can diverge. Fix is always: re-sum from transactions.

### 4. Template library seeded as DB data, not code

Department templates (Kitchen, F&B, Housekeeping, etc.) are rows in `department_templates`, not hardcoded TypeScript. This means: (a) a new template can be added by a SQL migration with no code deployment, (b) operators can inspect and override templates without modifying code, and (c) the template library grows independently of the application. New department types (e.g., a Wildlife department specific to game reserves) are a seed migration, not a code change.

### 5. Payments method-agnostic from day one

The `payments` table has a `method` field but the same schema regardless of method. Cash payments and MTN MoMo payments produce identical records — the only difference is that MTN MoMo records arrive via webhook (auto-reconciled) while cash is manually entered. This means V2's addition of Airtel Money and Stripe is a new webhook handler and a new `method` enum value — not a schema change.

### 6. Intelligence flags as first-class records

Alerts and anomalies are not ephemeral. They are rows in `intelligence_flags` with a lifecycle (open → acknowledged → resolved). This means: (a) the morning brief can reference them by ID, (b) history is preserved for audit, (c) admin can filter by severity/type/status, (d) resolution is a tracked action. The alternative (generating alerts dynamically on each dashboard load) is simpler but produces no audit trail and cannot track acknowledgement.

## What it does not do (V1)

- **Point of Sale** — restaurant/retail POS is V2. Invoices exist in V1 for accommodation billing only.
- **Reservations/bookings** — full booking system is V3.
- **Full accounting** — BMS tracks operational income and costs, not double-entry accounting. QuickBooks/Wave integration for full accounting is V4+.
- **HR and payroll** — staff records exist (users table) but payroll processing is V4+.
- **Stripe / international card payments** — the schema supports it; the integration is V2.
- **WhatsApp Business API** — researched and designed for, but requires Meta business verification. V1 includes the infrastructure (webhook endpoint, Edge Function) but activating the channel depends on verification completing. Notifications fall back to in-app only if WhatsApp is unavailable.
- **Multi-property dashboard** — an owner with two lodges has two separate org accounts in V1. Cross-property reporting is V4+.

## How it grows

### V2 — Point of Sale

V2 adds restaurant/retail POS, full invoicing with payment links, and Airtel Money + Stripe. The V1 schema is ready: `invoices` and `payments` already exist and are method-agnostic. V2 adds a `pos_orders` table and a `pos_line_items` table that link to `stock_items` for automatic ingredient deduction. The intelligence layer gains a new trigger: POS sale against a stock item with zero inventory fires a flag.

### V3 — Reservations & Guest Portal

V3 adds a `reservations` table, a `rooms` table, and a guest-facing portal. The `invoices` table gains a `reservation_id` FK. The morning brief gains an occupancy metric (count of checked-in reservations vs. room_count). No schema changes needed to what already exists.

### V4+ — Accounting, HR, Multi-property

Full P&L emerges naturally: revenue from `payments`, costs from `stock_transactions` + `purchase_orders`. The accounting module aggregates data already in BMS. HR/payroll adds a `payroll_records` table. Multi-property adds an `owner` entity above `organisations`.
