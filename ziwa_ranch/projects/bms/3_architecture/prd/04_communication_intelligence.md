# PRD 04 — Communication & Intelligence

> **Covers:** Threaded communication (threads, messages, mentions, notifications), intelligence flags, morning brief (scheduled generation and dashboard display), and on-demand department analysis.

---

## What we're building

Two connected modules:

**Communication** — a structured internal messaging system. Org-wide threads, department-specific threads, @mentions, and a notification centre. Replaces WhatsApp groups for operational communication without requiring staff to install a separate app.

**Intelligence** — the product's core differentiator. A nightly scheduled job aggregates all operational data and generates a morning brief waiting for the GM when they open BMS each day. Intelligence flags surface anomalies in real time. On-demand analysis lets an admin ask deep questions about any department's last N days.

---

## Why

### Communication
Most Ugandan lodges coordinate via WhatsApp groups. This works but leaves no record, has no structure, and cannot be linked to operational data. BMS's communication module creates a searchable, accountable record of operational decisions and is connected to the data (e.g., a flag can link directly to a stock shortfall that prompted the discussion).

### Intelligence
The Rafiki Lodge fraud case, the absence of cross-department data analysis at 40% of surveyed hotels, and the complete absence of operational intelligence in every local competitor (including Karibu) all point the same way: the GM who opens BMS every morning and sees what matters — without digging — will not leave BMS. The morning brief is the daily habit that makes the product sticky and irreplaceable.

## Requirements

### Threads and messages

**R4.1** — An admin or manager can create a thread at `/communication/new`. Thread types: `general` (visible to all org users), `announcement` (read-only for non-admin users), `department` (visible only to the department's assigned users and admins).

**R4.2** — All org users can view `general` and `announcement` threads. Only users assigned to a department (or admin/manager) can view `department` threads.

**R4.3** — Any user with access to a thread can post a message. Messages support plain text and @mention of other users in the organisation.

**R4.4** — @mentions are typed by entering `@` followed by a name. A dropdown of matching users appears. Selecting a user inserts their mention and records their `id` in `messages.mentions`.

**R4.5** — Messages support file and photo attachments. Attachments are uploaded to Supabase Storage. The message stores the URL, name, and type.

**R4.6** — Admins can pin threads. Pinned threads appear at the top of the thread list.

**R4.7** — The thread list is ordered by most recently active (most recent message first), with pinned threads above.

### Notifications

**R4.8** — A user receives a notification for each of the following events:
  - They are @mentioned in a message or review comment
  - A requisition they submitted changes status (approved / rejected / fulfilled)
  - An admin responds to their report (review comment)
  - A new `morning` brief is ready (admin and manager roles only)
  - A new `critical` intelligence flag is created (admin and manager roles only)

**R4.9** — Notifications appear in a notification centre accessible from the main navigation (bell icon with unread count badge).

**R4.10** — Clicking a notification navigates the user to the relevant resource (the report, the requisition, the thread, or the brief).

**R4.11** — A user can mark all notifications as read. Individual notifications are marked read when clicked.

**R4.12** — The notification centre loads instantly from Supabase Realtime subscription — new notifications appear without a page refresh.

### Intelligence flags

**R4.13** — Intelligence flags are generated by database triggers (see PRD 03 for stock triggers) and by the morning brief Edge Function. They are displayed on the admin dashboard and at `/intelligence`.

**R4.14** — Flags have severity levels: `info`, `warning`, `critical`. The dashboard prominently displays `critical` flags above all other content.

**R4.15** — An admin or manager can acknowledge a flag (status: `open` → `acknowledged`). Acknowledging requires no reason, but the acknowledgement is recorded with `acknowledged_by` and `acknowledged_at`.

**R4.16** — An admin or manager can resolve a flag (status → `resolved`). Resolved flags are hidden from the active dashboard view but remain in the flag history.

**R4.17** — The flag history at `/intelligence` shows all flags (open, acknowledged, resolved) filterable by type, severity, and status.

**R4.18** — The following flag types are generated automatically:
  - `stock_below_min` — triggered by stock_transactions trigger (PRD 03)
  - `stock_deficit` — triggered by stock_transactions trigger (critical severity)
  - `stock_discrepancy` — triggered by purchase_order save (PRD 03)
  - `report_overdue` — triggered by morning brief job for departments that did not submit by the schedule hour
  - `report_flagged` — triggered when an admin flags a report (PRD 02)
  - `na_spike` — generated by morning brief job when a department marks more than 3 sections N/A in a single report

### Morning brief

**R4.19** — A Supabase Edge Function `generate-morning-brief` is called daily at 05:00 UTC by pg_cron. It runs for all active organisations.

**R4.20** — For each organisation, the function aggregates:
  - Yesterday's reports: which departments submitted, which did not, any flagged reports
  - Stock movements: any items that fell below minimum, any purchase orders received
  - Open intelligence flags: count and summary by severity
  - Payments recorded yesterday: total cash + total mobile money

**R4.21** — The function calls GPT-4o with the aggregated data and produces a 2–3 paragraph narrative (`ai_narrative`) written for a GM: plain language, specific numbers, what needs attention today.

**R4.22** — The function writes the brief to `intelligence_briefs` with `brief_date = yesterday`, `brief_type = 'morning'`. If a brief for that org and date already exists (e.g., due to a retry), it is upserted.

**R4.23** — If the GPT-4o call fails, the brief is written with `status = 'failed'` and `ai_narrative = null`. The structured `alerts`, `summary`, and `trends` fields are populated regardless of the AI call success — the brief is useful even without the narrative.

**R4.24** — The morning brief is the landing screen for admin and manager users. When a user with admin or manager role logs in and navigates to the dashboard, the brief for today is displayed at the top.

**R4.25** — The brief display has three visible sections without scrolling:
  - **Alerts** — the open `critical` and `warning` flags, listed by severity. Each has a one-line description and a link to the relevant resource.
  - **Yesterday at a glance** — key metrics from `brief.summary`: submission rate (e.g., "7 of 8 departments submitted"), stock alerts count, total payments.
  - **AI narrative** — the GPT-4o paragraph, or "Brief narrative unavailable" if the AI call failed.

**R4.26** — The brief history at `/intelligence/briefs` shows all past briefs. A user can open any past brief and read the full content.

### On-demand analysis

**R4.27** — An admin can trigger a department analysis from the report list or the intelligence page. They select a department and a date range (up to 90 days). The system calls the `analyse-department` Edge Function.

**R4.28** — The `analyse-department` function fetches all reports for the department in the date range, constructs a prompt with the data, calls GPT-4o, and returns a structured analysis: trends observed, anomalies detected, recommendations.

**R4.29** — The on-demand analysis result is displayed inline. It is not persisted (it is a live query, not a stored record).

**R4.30** — If the analysis call takes more than 10 seconds, a progress indicator is shown. If it fails, a clear error message is shown with a retry option.

## Done when

- [ ] Threads can be created, messages posted, and @mentions work with notifications
- [ ] The notification centre updates in real time without a page refresh
- [ ] Intelligence flags are created by triggers (stock below min, report overdue) and appear on the dashboard
- [ ] An admin can acknowledge and resolve flags
- [ ] The morning brief Edge Function runs successfully in a test environment and produces a brief with all three sections
- [ ] The morning brief appears on the admin dashboard on first login after 8:00 AM
- [ ] On-demand department analysis runs and returns a result within 30 seconds
- [ ] All screens work on 375px mobile

**V2+ note:** The morning brief will gain an occupancy metric when reservations are added in V3. The `summary` JSONB field is designed to be extended — new metrics are added to the JSONB without a schema migration. The brief display component should render whatever keys are present in `summary`, not hardcode the expected keys.
